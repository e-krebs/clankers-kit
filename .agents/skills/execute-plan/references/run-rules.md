# Rules for the running session

The session that runs a plan, the one at the tier that `~/.agents/workflow-models/tiers.md` marks for running a plan, reads this file before the first row, and runs the plan by it. `<repo>` is the
plan header's `Repo:` path, `<plan>` is the plan file's absolute path, and `<stem>` is the plan path without `.md`, so the briefs are the files `<stem>.briefs/S<n>.md`. The Briefs section of `<plan>` holds either a `Briefs:` pointer line, so the briefs are the files in `<stem>.briefs/`, or `### S<n>` headings, so the briefs are inline in `<plan>`.

Start check, before row 1: read this session's model and effort from its own context. Compare them with the `run` row of `~/.agents/workflow-models/tiers.md` and with the provider's file (`claude.md` in Claude Code, `codex.md` on Codex). On a mismatch, stop and report both values. Run no row.

1. Run the rows in order. A row starts once every row in its After cell is `✅`. Rows that are ready together run in parallel. Set a row to `▶️` when it starts with `bash ~/.agents/skills/execute-plan/scripts/set-state.sh <plan> S<n> ▶️`. Never edit the Steps table by hand.
2. Dispatch every row whose Tier is not `<tier of the running session>` with `subagent_type` set to that tier and this prompt: "Work in <repo>. Read <stem>.briefs/S<n>.md, plus every file that brief links. Do S<n> only, and edit only the files in its row. Return the four-line report: `S<n> done|blocked`, `files:` the changed paths or none, `check:` the Done-when command, `->`, and its exit code, `off-plan:` one line or none." In a plan with inline briefs, the prompt reads `### S<n> in <plan>` instead of `<stem>.briefs/S<n>.md`. For a row whose work is a change across components or judging a diff, the prompt also names ## Summary and ## Decisions to read. Any other row reads its brief only. Append the row's line from the Steps table, and the reports of the rows in its After cell. For a fix row, which has no brief, the prompt says to read the row's Task cell instead of the brief, and to add a fifth report line `lines:` with the count of changed lines, which rule 7 reads. The `check:` line of a Gates report holds only the failing lines, never a full log.
   - A row whose brief's first line says `Provider: codex` runs as `codex exec --sandbox workspace-write -m <model> -c model_reasoning_effort=<effort> "<prompt>"`, with the tier's model and effort from `~/.agents/workflow-models/codex.md`, and the same prompt and report format. Run it in the background when rows run in parallel. In a Codex session, a row that says `Provider: claude` goes to the claude subagent of its tier. When the other provider is not installed, dispatch the row on the session's own provider.
   - Provider balance: a row is eligible when its Tier is above the tiers whose shape is a bare command or an established local pattern in `tiers.md`, no row that runs in parallel shares its files, its brief stands alone, and it is not S0, Review, Gates, Approval or Hand-off. Count the eligible rows that carry no `Provider:` line in row order. Send the 1st, 2nd, 3rd and 4th of each group of five to the other provider (codex in Claude Code, claude in Codex) and keep the 5th on the session's provider. A `Provider:` line pins its row and is not counted. A row that comes back blocked by its sandbox reruns once on the session's own provider, and that rerun is not a fix. With no other provider installed, every row stays on the session's provider.
3. Read the brief of a row at the running session's tier when that row starts, if it has one. With none, run the row from its Task cell. Read no other brief. To check a worker, read no attachment, and no source file, diff or full log. The Done-when result in its report is the evidence. The one exception is the line ranges a review finding cites, read during triage.
4. When a check fails, dispatch one fix worker with the failing lines, at a tier you pick from `~/.agents/workflow-models/tiers.md` for a change with the design settled, or at the owning row's tier when that is lower, on the session's provider. After a second failure, stop and report.
5. Set the row to `✅` when it is done, with `set-state.sh <plan> S<n> ✅`, so a fresh session with the same prompt resumes at the first row that is not `✅`. On a resume, run the Done-when check of a `▶️` row first. The row becomes `✅` on a pass, and runs again on a fail. Before you set `✅` on a row that a later After cell names, save its four-line report as `<stem>.briefs/S<n>.report.md`. A fresh session reads those files on a resume. A file change after the Gates row is `✅` resets Gates and Approval to `➖` with `set-state.sh`. Review stays `✅`, except as rule 7 says. A fix that the Review row sends lands before Gates runs, so Review does not run again for it.
6. Send each review finding you accept to a worker at a tier you pick from `~/.agents/workflow-models/tiers.md` for a change with the design settled, or at the owning row's tier when that is lower. Apply none yourself.
7. At the Approval row, write the working-tree summary as a message, then ask through the question tool in one phrase of 12 words at most. On feedback, insert fix rows before the Review row, and add them to the After cells of Review and Gates. Give each fix row the feedback as its Task and no brief. Then reset Gates and Approval to `➖` with `set-state.sh`. When the fix rows change more than 20 lines in all, reset Review to `➖` too. Run the Hand-off row only on the user's go-ahead, and pass the ticket key from the header to the PR skill.

The run has no cap on workers. The last reply of a run adds one line: `workers: <n> dispatched, <m> fix`.
